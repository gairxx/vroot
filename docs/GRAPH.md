# The vroot project graph

`vroot` is a tool for agents, so its own repository is machine-readable too. The
project graph records what exists (commands, recipes, flags, docs, decisions),
how those things relate, and what a change would touch. It lives in git as plain
JSONL so it can be reviewed, queried and proposed as a pull request.

```console
$ python3 tools/graphctl stats
278 nodes, 451 edges
$ python3 tools/graphctl impact flag:python
```

## Files

| Path                 | Role                                                    |
| -------------------- | ------------------------------------------------------- |
| `graph/nodes.jsonl`  | source of truth: one `{id, kind, attrs}` object per line |
| `graph/edges.jsonl`  | source of truth: one `{src, rel, dst, attrs}` per line   |
| `graph/index.sqlite` | derived, git-ignored; rebuilt by `graphctl index`        |
| `tools/graphctl`     | the only writer; Python 3, standard library only         |

Both files are sorted (`id` for nodes, `src,rel,dst` for edges), one object per
line, keys sorted. That makes diffs minimal and lets `graphctl guard` detect
drift byte for byte. Never hand-edit them in an order you cannot reproduce: run
`python3 tools/graphctl ingest --write` instead.

`ingest` regenerates everything it can derive. Entries created with `add` and
`link` carry `"origin": "declared"` in their attributes and are preserved across
regeneration; if a declared edge loses an endpoint because the target was
removed, `ingest` drops it and says so on stderr. This is how judgement edges
(`affects`, `supersedes`, `depends_on`) survive a rebuild.

## Node kinds

| Kind       | Example id                 | Meaning                              |
| ---------- | -------------------------- | ------------------------------------ |
| `repo`     | `repo:vroot`               | the project                          |
| `module`   | `module:vroot`             | a source file that contains code     |
| `function` | `function:build_env`       | a top-level shell function           |
| `command`  | `command:build`            | a user-facing CLI command            |
| `recipe`   | `recipe:python`            | one `.conf` recipe                   |
| `flag`     | `flag:python`, `flag:py`   | a flag or alias that selects it      |
| `base`     | `base:alpine`, `base:debian` | a rootfs base                      |
| `doc`      | `doc:docs/AGENTS.md`       | a documentation file                 |
| `section`  | `section:docs/AGENTS.md#the-model` | a heading inside a doc      |
| `adr`      | `adr:0001-project-graph`   | an architecture decision record      |

IDs are `kind:name`. Recipe and flag names match the CLI (`-python`, `-node`),
doc ids are repository-relative paths, and section ids append a slug of the
heading, so links stay stable when sections move within a file.

## Relations

| Relation     | Direction             | Meaning                                  |
| ------------ | --------------------- | ---------------------------------------- |
| `contains`   | parent → child        | structural membership                    |
| `provides`   | recipe → flag         | this recipe answers this flag/alias      |
| `based_on`   | recipe → base         | rootfs the recipe builds on              |
| `documents`  | recipe → doc          | recipe declares a docs page              |
| `mentions`   | doc/section/adr → flag | text references the flag's `-form`     |
| `affects`    | adr → target          | decision governs the target (declared)   |
| `supersedes` | adr → adr             | newer decision replaces an older one     |
| `depends_on` | target → target       | explicit requirement (declared)          |

Structural relations (`contains`, `provides`, `based_on`, `mentions`,
`documents`) are generated by `ingest`. Judgement calls (`affects`,
`supersedes`, `depends_on`) are added by hand in the same PR that motivates
them, with `graphctl link`.

## Commands

```console
$ python3 tools/graphctl help
$ python3 tools/graphctl schema --json
```

Read side:

```console
$ python3 tools/graphctl get recipe:python
$ python3 tools/graphctl list --kind recipe
$ python3 tools/graphctl query --from recipe:node --depth 2 --dir both
$ python3 tools/graphctl impact flag:python          # who breaks if this changes
$ python3 tools/graphctl path repo:vroot base:debian
$ python3 tools/graphctl stats --json
$ python3 tools/graphctl sql "select id from nodes where kind='recipe' order by id"
$ python3 tools/graphctl export --format mermaid
```

Write side (the graph is locked while writing, so parallel agents cannot
interleave):

```console
$ python3 tools/graphctl add adr:0003-foo title="Foo" status=proposed
$ python3 tools/graphctl link adr:0003-foo affects recipe:python
$ python3 tools/graphctl set recipe:python description="Python 3 toolchain"
$ python3 tools/graphctl unlink adr:0003-foo affects recipe:python
$ python3 tools/graphctl rm adr:0003-foo --cascade
```

Regeneration and checks:

```console
$ python3 tools/graphctl ingest            # report drift, exit 1 if stale
$ python3 tools/graphctl ingest --write    # regenerate from the repository
$ python3 tools/graphctl check             # structural validation
$ python3 tools/graphctl guard             # ingest + compare (used by CI)
$ python3 tools/graphctl index             # rebuild graph/index.sqlite
```

Every command accepts `--json`. Errors print one `err: …` line on stderr and
exit 1, matching the CLI contract in `docs/AGENTS.md`.

## Cookbook

**What does this flag drag in?** (recipe, base, packages, docs)

```console
$ python3 tools/graphctl query --from flag:python --dir in --depth 1 --json
```

**What breaks if I delete a function?** (`impact` walks reverse edges)

```console
$ python3 tools/graphctl impact function:build_env --json
```

**Which recipes does the agent guide mention?**

```console
$ python3 tools/graphctl sql "select distinct e.dst from edges e \
    join nodes n on n.id = e.src \
    where e.rel='mentions' and n.id like 'section:docs/AGENTS.md%' order by 1"
```

**Which base do most recipes use?**

```console
$ python3 tools/graphctl sql "select dst, count(*) c from edges \
    where rel='based_on' group by dst order by c desc"
```

**Is every flag documented somewhere?**

```console
$ python3 tools/graphctl sql "select id from nodes where kind='flag' and id not in \
    (select dst from edges where rel='mentions') order by id"
```

## Adding a recipe end to end

1. Add `recipes/<name>.conf` with `name`, `provides`, `base`, `description`.
2. Run `python3 tools/graphctl ingest --write`. The new `recipe:<name>`,
   `flag:*` nodes and `provides`/`based_on` edges appear in the diff.
3. Mention the flag in `docs/RECIPES.md` (or the site) so a `mentions` edge
   records where it is explained.
4. Run `make graph-check` before opening the pull request.

The same loop applies to a new command (`cmd_*` in `vroot`), a new doc heading,
or a new decision record under `docs/decisions/`.

## Drift and review

`graphctl guard` rebuilds the graph in memory from the repository and compares it
to the committed files. CI fails if anything differs, so a PR that changes a
recipe but not the graph cannot merge. Because the graph is committed JSONL, the
reviewer sees the semantic change (two nodes, three edges) next to the code that
caused it.

Judgement edges are the only part automation cannot verify. Add them when you
make the decision they describe; a reviewer can reject them like any other line
of the diff. `docs/decisions/` holds the rationale for the graph itself.

## Design notes

- **JSONL in git, SQLite on demand.** Review happens in a diff; a server would
  add an availability dependency to a tool whose point is not needing one.
  `graphctl index` builds a throwaway index for recursive queries.
- **Generated vs. declared.** Anything derivable from the repository is
  generated, so it cannot rot. Anything that encodes a judgement is declared with
  `add`/`link`, preserved by `ingest`, and reviewed like any other line.
- **Strict validation.** `check` refuses unknown kinds, unknown relations,
  dangling edges and duplicates; `ingest` will not write a graph that fails it.
- **Deterministic output.** Sorted keys, sorted lines, no timestamps. Two
  machines that ingest the same commit produce byte-identical files.
- **Stable ids over stable files.** Section ids follow heading slugs, so a
  renamed heading is a deleted node plus an added node — a visible event in the
  diff, not a silent link rot.
